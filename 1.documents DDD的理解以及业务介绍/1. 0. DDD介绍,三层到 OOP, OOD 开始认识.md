# 从三层到 OOP, OOD 开始认识，这里提到的 OOP 和 OOD 是什么

## OOP - 面向对象编程

OOP（Object-Oriented Programming） 是一种编程范式，它使用"对象"来设计软件和应用程序。
OOP 的四大支柱：

1. 封装
   概念：将数据和对数据的操作捆绑在一起，并隐藏内部实现细节
2. 继承
   概念：子类可以继承父类的特性和行为，并添加新的功能
3. 多态
   概念：同一操作作用于不同对象，可以有不同的解释和执行结果
   例子：

```
Animal myAnimal = new Dog();
myAnimal.eat(); // 实际调用的是Dog的eat方法
```

4. 抽象

   - 概念：隐藏复杂实现，只暴露必要的接口

   - 例子：使用接口或抽象类定义契约

## OOD - 面向对象设计

OOD（Object-Oriented Design） 是设计阶段的活动，关注如何用面向对象的概念来设计软件架构。

OOD 的核心原则（SOLID 原则）：

1. 单一职责原则

- 一个类应该只有一个引起变化的原因

- 三层架构体现：Controller 只处理 HTTP，BLL 只处理业务逻辑，DAL 只处理数据访问

2. 开闭原则

- 对扩展开放，对修改关闭

- 例子：通过继承或接口扩展功能，而不是修改现有代码

3. 里氏替换原则

- 子类应该能够替换父类而不影响程序正确性

4. 接口隔离原则

- 不应该强迫客户端依赖它们不用的接口

5. 依赖倒置原则

- 高层模块不应该依赖低层模块，两者都应该依赖抽象

## 里氏替换原则 学习

常见误解和正确理解：
违反 LSP 的经典例子（矩形-正方形问题）

```
// 违反LSP的代码 - 看起来合理，实际有问题
public class Rectangle
{
    public virtual int Width { get; set; }
    public virtual int Height { get; set; }

    public int CalculateArea() => Width * Height;
}

// Square "是" Rectangle吗？数学上是的，但程序行为上不是！
public class Square : Rectangle
{
    public override int Width
    {
        get => base.Width;
        set
        {
            base.Width = value;
            base.Height = value; // 这里破坏了父类的约定！
        }
    }

    public override int Height
    {
        get => base.Height;
        set
        {
            base.Height = value;
            base.Width = value; // 这里也破坏了父类的约定！
        }
    }
}

// 测试代码 - 会出现意外行为
public void TestRectangle(Rectangle rect)
{
    rect.Width = 5;
    rect.Height = 4;

    // 如果是Rectangle：面积应该是20
    // 如果是Square：面积会是16（最后设置Height=4，Width也会变成4）
    Console.WriteLine($"Area: {rect.CalculateArea()}");
}

// 使用
var rect = new Rectangle();
TestRectangle(rect); // 输出: Area: 20

var square = new Square();
TestRectangle(square); // 输出: Area: 16 ❌ 这不是我们期望的！
```

如何正确实现 LSP：
方案 1：使用组合代替继承

```
public interface IShape
{
    int CalculateArea();
}

public class Rectangle : IShape
{
    public int Width { get; set; }
    public int Height { get; set; }

    public int CalculateArea() => Width * Height;
}

public class Square : IShape
{
    public int SideLength { get; set; }

    public int CalculateArea() => SideLength * SideLength;
}

// 现在它们都能被正确使用
public void ProcessShapes(List<IShape> shapes)
{
    foreach (var shape in shapes)
    {
        Console.WriteLine($"Area: {shape.CalculateArea()}");
    }
}
```

方案 2：如果必须继承，确保行为一致

```
public abstract class Shape
{
    public abstract int CalculateArea();
}

public class Rectangle : Shape
{
    public int Width { get; set; }
    public int Height { get; set; }

    public override int CalculateArea() => Width * Height;
}

public class Square : Shape
{
    public int SideLength { get; set; }

    public override int CalculateArea() => SideLength * SideLength;
}
```

实践：多用接口，少用继承；如果必须继承，确保不修改父类行为
行为约定（Behavioral Contract）

```
public class Rectangle
{
    // 隐含的约定：
    // 1. Width和Height是独立的属性
    // 2. 设置Width不会改变Height
    // 3. 设置Height不会改变Width
    // 4. Area = Width × Height

    public virtual int Width { get; set; }  // 只影响Width
    public virtual int Height { get; set; } // 只影响Height

    public int CalculateArea() => Width * Height;
}
```

## 依赖倒置（正确）：

```
// 第一步：高层（业务逻辑层）定义需要的接口
// 这是关键！接口由使用方（高层）定义，而不是提供方（低层）
namespace Domain.Abstractions  // 在领域层（高层）
{
    // 高层说："我需要这样访问订单数据"
    public interface IOrderRepository
    {
        // 用业务对象Order，不是数据库对象
        void SaveOrder(Order order);
        Order GetOrder(int id);
    }
}

// 第二步：高层实现业务逻辑
namespace Application.Services  // 应用层（高层）
{
    public class OrderService
    {
        private readonly IOrderRepository _orderRepository;

        public OrderService(IOrderRepository orderRepository)
        {
            _orderRepository = orderRepository;
        }

        public void ProcessOrder(Order order)
        {
            // 直接使用业务对象，不用转换！
            _orderRepository.SaveOrder(order);
        }
    }
}

// 第三步：低层实现高层定义的接口
namespace Infrastructure.Data  // 基础设施层（低层）
{
    // 数据访问层说："我来实现高层定义的接口"
    public class SqlServerOrderRepository : IOrderRepository
    {
        public void SaveOrder(Order order)
        {
            // 这里负责把Order转成数据库格式
            var sqlOrder = ConvertOrderToSqlFormat(order);
            // SQL Server特定代码
        }

        private SqlOrder ConvertOrderToSqlFormat(Order order)
        {
            // 转换逻辑在低层，不影响高层
        }
    }
}

// 第四步：另一个低层实现（比如测试用的）
namespace Tests.Mocks
{
    public class InMemoryOrderRepository : IOrderRepository
    {
        private List<Order> _orders = new();

        public void SaveOrder(Order order)
        {
            // 内存实现，用于测试
            _orders.Add(order);
        }
    }
}
```

依赖倒置方式：
你（高层）定义菜单（接口）：

public interface IMeal
{
void Serve();
}

然后说："我要一个符合这个接口的餐"

厨师 A 可以给你面条

厨师 B 可以给你米饭

厨师 C 可以给你汉堡

你控制菜单（接口），厨师们实现它！

## OOP vs OOD 的关系

```

方面  	OOP（编程）         	   OOD（设计）
关注点	 如何实现代码	         如何设计软件结构
阶段	   编码阶段	               设计阶段
产出	   具体的类、方法、对象	    类图、架构设计、关系设计
工具	   编程语言（Java/C#等）	UML图、设计模式
```

## 实际关系：

OOD 是蓝图（设计房子）

OOP 是施工（建造房子）
